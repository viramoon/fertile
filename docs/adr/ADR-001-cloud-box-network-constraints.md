# ADR-001：云电脑网络与运行环境约束、部署策略

状态：已采纳（2026-11-12）
适用范围：fertile 系统全部仓库（fertile / finance / web / frontend / agent）

## 1. 背景与决策

在相当长一段时间内，所有开发成果只运行在当前云电脑上，交易一律使用 IBKR **paper 账户**。系统稳定且效果好之后，再迁移到专用机器（VPS 或自有服务器）用实盘账户运行。

本阶段设计原则：
1. **在当前网络下尽可能增强稳定性**：所有长连接可检测、可恢复、可核对状态。
2. **不为当前环境牺牲迁移后的性能**：环境相关处理全部做成可配置的适配层，迁到稳定网络后通过配置关闭或放宽，不改业务代码。
3. **目标形态按“方案三”设计**：云电脑负责开发和分析；IB Gateway、实时行情采集、订单执行、订单状态、网站/Webhook 入口在迁移后放到稳定服务器。现阶段先跑在云电脑上，但模块边界按可拆分来划。

## 2. 已观察到的现象（附证据边界）

| 现象 | 已确认 | 未确认 / 不能推出 |
|---|---|---|
| Cloudflare Tunnel 用 HTTP/2 时，4 条连接约 4 分钟后同一秒断开，未自行恢复；外部 502/530，本地探测仍 200 | 现象本身 | 不能确认“代理固定每 4 分钟断 TCP”；空闲超时、连接寿命、共享代理重启、路径异常、边缘端或客户端问题均待排查 |
| 改用 QUIC 后 8 分钟未断；已加守护脚本，目标在异常后 15～30 秒触发恢复 | 短期测试结果 | 未做长期验证；恢复时间不是可用性保证 |
| 出口 IP 不稳定，不同流量可能走不同出口 | 查 IP 网站结果会变 | 不等于交易 API / SSH 的实际源地址；“新连接换 IP”不等于“连接中途换 IP” |
| IBKR、Nasdaq 部分 HTTPS 地址可访问；Binance 国际站 API 返回 451（当时出口在美国） | 单次 HTTP 结果 | 不代表认证、行情订阅、交易接口、IB Gateway/TWS 长连接可用 |
| 平台确认部分非 HTTPS 出站异常；存在共享出口 | 平台工作人员说明 | 具体受影响端口和协议范围未知 |
| 2026-11-12 云电脑重启后，`/srv`、`/etc/systemd/system` 下新建内容全部丢失，`/home/box` 下内容保留 | 本次观察 | 平台持久化规则未经官方确认；按“只有 /home/box 持久”处理 |

## 3. 风险与对策

| 风险 | 业务影响 | 对策（本阶段实现） |
|---|---|---|
| 长连接中断或失去响应 | 行情停更、隧道不可用、交易状态中断 | 应用层心跳 + 读超时 + 指数退避重连；外部端到端健康检查（从公网访问域名，不只看本地 200） |
| 重连后状态不完整 | 漏行情、订阅丢失、订单状态过期 | 重连后自动：重建订阅 → 按断点补历史数据 → 拉订单/持仓/账户快照并与本地核对 |
| 下单超时但实际已成交 | 盲目重试导致重复下单 | 每笔订单带客户端唯一 ID（orderRef）；下单请求**禁止无条件重试**，先查订单和成交再决定 |
| 出口 IP 变化 | 白名单拒绝、会话失效、额外验证 | 不依赖 IP 白名单；会话失效可自动重新认证；记录每次连接实际观察到的源 IP（服务端可见时） |
| 共享出口 | 被他人触发的限流/封禁波及 | 限流退避、错误分类、监控；**不通过换 IP 绕过限制** |
| 出口地区不符合平台服务范围 | 地区拒绝、合规风险 | 只接入账户资格和服务地区确认无误的平台；返回 451 的服务（如 Binance 国际站）不接入 |
| 依赖隧道接收外部请求 | 网站、Webhook 在断开期间不可达 | 网站只做展示和低风险操作；交易不依赖外部入站请求触发；Webhook 输入落盘持久化 + 幂等去重 |
| 云环境重启、回收、文件不持久 | 进程停机、配置和运行状态丢失 | 代码、配置、数据、日志、二进制只放 `/home/box` 下；系统级改动（/etc、/srv、/usr）视为每次重启都要重做，必须写进可重复执行的初始化脚本；状态只存数据库；定期备份；进程启动时从数据库恢复状态 |

## 4. 设计规则（所有模块必须遵守）

1. **连接层统一抽象**：所有外部长连接（IB Gateway、行情 WebSocket、数据源）通过统一的连接管理器，提供心跳、超时、重连、重连后回调（重订阅、补数、对账）。超时、心跳间隔、重试策略全部写在配置里。
2. **两套重试策略**：读请求可幂等重试；写请求（下单、改单、撤单）必须“先查后试”，带唯一 ID。
3. **业务健康 ≠ 进程健康**：每个服务提供两层健康检查，`live`（进程活着）和 `ready`（关键依赖可用且数据新鲜，如行情最后更新时间在阈值内、Gateway 已认证）。
4. **行情陈旧熔断**：配置“行情最大允许陈旧时间”；超过阈值或订单状态不可靠时，策略自动暂停开新仓，只允许撤单和查询；恢复后对账通过才继续。
5. **入口与核心解耦**：web/frontend 不可用不影响 finance 交易核心；finance 不依赖 Tunnel。
6. **环境差异只在配置层**：`profile=cloudbox`（激进心跳、短超时、额外重试）与 `profile=stable`（迁移后），代码路径一致。
7. **持久化路径约定**：所有运行时路径从配置读取，默认根目录在 `/home/box` 下；不硬编码 `/srv`、`/etc` 等路径。
8. **可观测**：断线时间、恢复耗时、错误类型、源 IP（如可见）、行情延迟写入日志和指标，用于 24～72 小时验证报告。

## 5. 模块放置

| 模块 | 当前（云电脑 + paper） | 迁移后（实盘） |
|---|---|---|
| frontend、web（网站、blog） | 云电脑，经 Cloudflare Tunnel（QUIC + 守护） | 可留云电脑或随 VPS；不影响交易 |
| 数据分析、回测、研究 | 云电脑 | 云电脑（读历史数据，不在交易关键路径） |
| finance：IB Gateway、行情采集、订单执行、订单状态 | 云电脑（按可拆分边界实现） | 稳定服务器独立部署；云电脑通过 API 提交任务、读结果 |
| 数据库 | 云电脑，`/home/box` 下持久化 + 定期备份 | 交易相关库随交易核心迁移 |

不采用“云电脑 + 固定出口代理”作为长期方案：它只改善出口身份，交易进程到代理这一段仍可能断。

## 6. 上线前验证（每次大改动和迁移前都要做）

- 用真实业务协议连续测试 24～72 小时，覆盖美股交易时段；结论只作为初步验收。
- 同时测空闲连接和持续有数据的连接，记录断开时间、恢复耗时、错误类型、服务端看到的源 IP。
- 人为模拟断网、进程重启、认证失效、云电脑重启，验证行情补齐、订阅恢复、订单对账、重复下单防护、服务自动恢复。
- 明确并写入配置：行情最大允许陈旧时间、服务恢复目标、暂停交易规则。

## 8. v2 补充

交易核心基于 NautilusTrader，作为依赖使用、不 fork；连接、重连、重订阅和订单对账的部分职责由其 IB 适配器及执行引擎承担。finance 负责配置映射、版本验证、补数边界、幂等、行情陈旧熔断和恢复门禁，详见 [finance docs/connectivity.md](https://github.com/viramoon/finance/blob/main/docs/connectivity.md)。

v2 的行情存储为 Nautilus Parquet catalog，节点恢复状态的后端仍待实现验证；业务与博客 PostgreSQL 归 web。frontend 为 Vite 静态产物，由 web 托管，不单独起服务；以上细化原文的模块与状态边界，不改变只用 paper、持久路径、可拆分迁移和上线前验证原则。
